## 4. Findings

### P1-01 — CI has never been green: the Trivy image scan fails on every run

Evidence: runs 1–9 of the `CI` workflow all conclude `failure`. On the current head the
`verify` job (lint, typecheck, build, e2e) **passes**; only `image scan (Trivy)` fails, at the
step "Trivy — block on HIGH/CRITICAL" with exit code 1. The SARIF was uploaded to Code Scanning
but the table was not printed, so the exact HIGH/CRITICAL rows are only visible under
Security → Code scanning on GitHub. Two things are certain from a local reproduction:

- The placeholder Clerk key `pk_live_Y2xlcmsuZXRoYW5lbC50ZXN0JA` is inlined into 14 built files and
  Trivy's secret scanner reports each as a "Stripe publishable key" (LOW). Noise, but it fills the
  SARIF and Code Scanning with false alerts.
- The production dependency chain `@ethanel/db → @prisma/client → prisma → mysql2 / deepmerge-ts`
  carries two HIGH advisories with fixes available (P2-06). Whether they are inside the runtime
  image depends on Next's standalone pruning; the Debian 12.15 base layer is the other candidate.

Impact: `main` cannot be trusted as "green", branch protection cannot require CI, and the staging
deploy would ship an image the scanner rejected.

**Prompt 1 (run first):**

> Open Security → Code scanning for `main` and list every alert Trivy raised at HIGH or CRITICAL.
> Then in `.github/workflows/ci.yml`: set `scanners: vuln` on the trivy-action step so secret
> scanning of build output stops (the only "secret" is the CI placeholder key); add a
> `.trivyignore` only for advisories that are unfixable in the base image, with a comment and a
> review date each; bump the Node base image or the dependency named in each remaining alert.
> Re-run CI and confirm both jobs are green on `main`.

### P1-03 — The deploy workflows install a Helm _library_ chart, which Helm refuses

Evidence: `charts/service/Chart.yaml` has `type: library` and its templates are only `define`
blocks. `deploy-staging.yml` and `deploy-production.yml` run
`helm upgrade --install web ./charts/service …`. Helm rejects installing a library chart
("library charts are not installable"). The job is currently gated off by
`vars.STAGING_DEPLOY_ENABLED`, so the failure has not surfaced yet, but the first real deploy will
fail at the last step.

**Prompt 3:**

> Create an application chart for web (e.g. `apps/web/helm/Chart.yaml` with
> `dependencies: [{ name: service, repository: file://../../../charts/service }]` and a
> `templates/all.yaml` that `include`s `ethanel.service.deployment`, `…pdb`, `…networkpolicy`),
> point both deploy workflows at it, and add a CI step `helm lint` + `helm template` with
> `values.staging.yaml` so the rendered manifests are checked on every PR.

### P2-01 — Open redirect through a backslash in `/sign-in?next=`

Evidence: `safeNext()` in `apps/web/app/(auth)/sign-in/[[...sign-in]]/page.tsx` accepts
`next=/\evil.com` (regex `^\/(?!\/)[^\s]*$` only rejects a second forward slash). The value is
rendered as `data-next="/\evil.com"` and passed to Clerk as `forceRedirectUrl`. Browsers and the
WHATWG URL parser treat `/\evil.com` as `//evil.com`, so after sign-in the visitor can be sent
off-site. Probed variants: `/marketplace` ok, `//evil.com` rejected, `https://evil.com` rejected,
`/%09/evil.com` rejected, `/\evil.com` **accepted**.

**Prompt 4:**

> Harden `safeNext`: reject any value containing `\`, and additionally resolve it with
> `new URL(value, 'http://x')` and require `origin === 'http://x'` and `pathname.startsWith('/')`.
> Add to `packages/testing/e2e/auth.spec.ts` a table test that `/\evil.com`, `//evil.com`,
> `/%5Cevil.com`, `https://evil.com` and `javascript:alert(1)` all render without `data-next`.

### P2-02 — No security response headers

Evidence: `curl -I /` on the production build returns no `Strict-Transport-Security`,
`Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`,
`Referrer-Policy` or `Permissions-Policy`. `poweredByHeader` is off (good). Cloudflare may add
some of these, but the app should not depend on it and the dashboard (money screens) must not be
frameable.

**Prompt 5:**

> Add a `headers()` block to `apps/web/next.config.ts` for `/(.*)`: HSTS (1 year, includeSubDomains,
> preload only once confirmed), `X-Content-Type-Options: nosniff`, `Referrer-Policy:
strict-origin-when-cross-origin`, `Permissions-Policy` denying camera/geolocation (microphone
> allowed on `self` for the assistant), and a CSP with `frame-ancestors 'none'` plus the Clerk,
> Unsplash and NVIDIA origins the app really uses. Start CSP in report-only, then enforce. Add a
> smoke test asserting the headers on `/` and `/org/riverside-lettings`.

### P2-03 — Rate limiting trusts a client-supplied header and answers 200

Evidence: `clientIpFrom()` takes the first hop of `X-Forwarded-For`. From one connection, 30 chat
calls with `X-Forwarded-For: 10.0.0.1` exhausted the limit; the 31st with `10.0.0.2` was served.
The refused chat response is an SSE stream with HTTP 200 and no `Retry-After`. The store is
per-process memory, so two replicas double every limit (documented Q-11/Q-31).

**Prompt 6:**

> Make `clientIpFrom` prefer `CF-Connecting-IP` (Cloudflare) and fall back to the _last_ hop of
> `X-Forwarded-For` only when a trusted proxy count is configured; never the first hop. Return
> HTTP 429 with `Retry-After` for JSON callers of the assistant routes (keep the SSE error event
> for the widget when `Accept: text/event-stream`). Record in `RISKS.md` that limits are
> per-replica until Valkey lands.

### P2-04 — First-contact account linking does not check the email is verified

Evidence: `getActor()` in `apps/web/lib/auth.ts` links a seeded `identity.users` row to any Clerk
user whose `primaryEmailAddress` matches, without reading `verification.status`. If the Clerk
instance ever allows an unverified email (a misconfiguration, or a social provider that returns an
unverified address), anyone can sign up as `demo.admin@ethanel.co.ke` or, later, as a real
organization owner, and be linked to that row.

**Prompt 7:**

> In `getActor`, only call `linkClerkUserByEmail` when
> `user.primaryEmailAddress.verification?.status === 'verified'`; log a `warn` and return null
> otherwise. Confirm in the Clerk dashboard that email verification is required for password
> sign-up. Add a unit test for the refusal path (see P3-04 for the unit-test layer).
